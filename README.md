# Process Management and Scheduling Extensions for xv6 RISC-V

This repository extends the educational xv6 operating system for RISC-V with process inspection, process scheduling controls, runtime accounting, and three compile-time scheduler implementations.

## Repository

- Project repository: <https://github.com/amirhdeh/xv6-riscv>
- Final branch: `ps-init`
- Upstream project: <https://github.com/mit-pdos/xv6-riscv>

Clone the final branch directly:

```sh
git clone --branch ps-init https://github.com/amirhdeh/xv6-riscv.git
cd xv6-riscv
```

## Features

- A shared `struct pinfo` contract for transferring process information from the kernel to user space
- A `getpinfo(struct pinfo *)` system call
- A `ps` command that shows PID, owner, priority, state, ticket count, runtime, and command name
- Numeric priorities from 0 to 100, where a smaller number means a higher priority
- Pseudorandom initial priorities in the range `0..100`
- A `setpriority(int pid, int priority)` system call and `chpri` shell command
- One initial scheduling ticket per process and ticket inheritance across `fork()`
- A `settickets(int pid, int number)` system call and `chtickets` shell command
- A kernel `PRNG()` based on a linear congruential generator seeded from `ticks`
- Per-process `RTIME` accounting while a process is in the `RUNNING` state
- A CPU-bound `spin` workload for scheduler experiments
- Three compile-time schedulers: original xv6, strict priority, and lottery
- Functional, statistical, concurrency, deadlock, fairness, and inheritance tests

## Process Information Model

The following fields were added to `struct proc` in `kernel/proc.h`:

| Field | Meaning |
|---|---|
| `owner` | Process owner identifier. It is currently 0 for every process because xv6 has no user-account model. |
| `priority` | Scheduling priority in `0..100`; 0 is the highest priority. |
| `tickets` | Weight used by the lottery scheduler; every active process has at least one ticket. |
| `runtime` | Number of timer interrupts received while the process was `RUNNING`. |

`kernel/pinfo.h` is shared by the kernel and user programs. It stores one entry for each process-table slot:

```c
struct pinfo {
  int inuse[NPROC];
  int pid[NPROC];
  int owner[NPROC];
  int priority[NPROC];
  int status[NPROC];
  int tickets[NPROC];
  int runtime[NPROC];
  char name[NPROC][16];
};
```

`struct proc` is not exposed directly because it contains kernel-only pointers, address-space state, file descriptors, contexts, and locks. `struct pinfo` is a restricted snapshot containing only information intended for user space.

## System Calls

Three system call numbers were added to `kernel/syscall.h`:

| Number | User interface | Purpose |
|---:|---|---|
| 23 | `getpinfo(struct pinfo *info)` | Copy a process-table snapshot to user space. |
| 24 | `setpriority(int pid, int priority)` | Change the priority of an existing process. |
| 25 | `settickets(int pid, int number)` | Change the ticket count of an existing process. |

Each system call follows this path:

```text
user program
  -> stub generated by user/usys.pl
  -> dispatch table in kernel/syscall.c
  -> sys_* wrapper in kernel/sysproc.c
  -> process-table logic in kernel/proc.c
```

### `getpinfo`

`sys_getpinfo()` performs these steps:

1. Reads the destination user address with `argaddr()`.
2. Zeroes a kernel-local `struct pinfo`.
3. Iterates over `proc[NPROC]`.
4. Acquires each process's `p->lock` before reading its fields.
5. Copies all active fields and the process name while that lock is held.
6. Releases the process lock before moving to the next slot.
7. Copies the completed structure to the caller with `copyout()`.

Each row is internally consistent, but the complete table is not one globally atomic snapshot. Process states can change between reading two different rows.

### `setpriority`

The kernel rejects priorities outside `0..100`. It then searches the process table while acquiring one `p->lock` at a time. A matching, non-`UNUSED` process is updated while its lock is held. An invalid value or unknown PID returns `-1` without changing the previous priority.

### `settickets`

The kernel rejects zero and negative ticket counts. It searches and updates the target under `p->lock`, using the same locking pattern as `setpriority`. An invalid value or unknown PID returns `-1` and leaves the previous ticket count unchanged.

The user commands validate their inputs to provide clear error messages, but validation is repeated in the kernel so correctness never depends on a well-behaved user program.

## Initialization and Inheritance

`allocproc()` initializes the scheduling fields as follows:

```text
owner    = 0
priority = PRNG() % 101
tickets  = 1
runtime  = 0
```

During `fork()`:

- The child inherits the parent's `owner`.
- The child inherits the parent's `tickets`.
- The child's `runtime` starts at 0.
- The child normally keeps the random priority generated by `allocproc()`.
- A direct child of `sh` temporarily receives priority 0 so it can reach `exec()` even under heavy strict-priority load.

During `exec()`:

- `sh`, `ps`, `kill`, `chpri`, and `chtickets` receive priority 0 so system control remains available.
- Other commands launched by `sh` receive a new random priority in `0..100`.
- `spin` is deliberately not considered an interactive command.

Changing a child's ticket count after `fork()` does not change its parent's ticket count. The values are copied integers, not shared state.

## Pseudorandom Number Generator

`PRNG()` in `kernel/proc.c` uses a linear congruential generator:

```text
state(n+1) = (1103515245 * state(n) + 12345) mod 2^32
```

On the first call, the protected kernel `ticks` value is used as the seed. Unsigned 32-bit overflow provides the `2^32` modulus naturally.

Locking rules:

- `rand_lock` protects `rand_state` and one-time initialization.
- `tickslock` protects the seed read from `ticks`.
- Concurrent calls from different CPUs cannot update the same old state or lose an update.

The generator is used for:

- Random initial priorities through `PRNG() % 101`
- Lottery selection by combining two 32-bit outputs into a 64-bit value

It is suitable for this educational scheduler but is not intended for security-sensitive random numbers.

## Selecting a Scheduler

The scheduler is selected at compile time with the `SCHEDULER` Make variable. If the variable is omitted, the original xv6 scheduler is used.

```sh
# Original xv6 scheduler; default
make qemu

# Explicit original xv6 scheduler
make qemu SCHEDULER=DEFAULT

# Strict-priority scheduler
make qemu SCHEDULER=PRIORITY

# Lottery scheduler
make qemu SCHEDULER=LOTTERY
```

Any other value is rejected by the Makefile. `kernel/proc.c` also contains a preprocessor check requiring exactly one of `DEFAULT`, `PRIORITY`, or `LOTTERY`.

`kernel/proc.o` and `user/pritest.o` depend on a forced rebuild target. Switching `SCHEDULER` therefore recompiles the files whose behavior depends on the selected macro, even without `make clean`.

## Scheduler Algorithms

### Original xv6 Scheduler (`DEFAULT`)

This is the unchanged scheduling loop from the upstream xv6 implementation:

1. Each CPU scans `proc[]` from beginning to end.
2. It acquires one process lock.
3. If the process is `RUNNABLE`, it changes the state to `RUNNING` and switches to it.
4. After the process returns to the scheduler, the lock is released and scanning continues.
5. If no process is runnable, the CPU waits for an interrupt with `wfi`.

The `priority` and `tickets` fields remain visible and changeable in this mode, but neither field affects process selection.

Simplified pseudocode:

```text
for each process in proc[]:
    acquire(p->lock)
    if p->state == RUNNABLE:
        p->state = RUNNING
        switch to p
    release(p->lock)

if nothing was runnable:
    wfi
```

### Strict-Priority Scheduler (`PRIORITY`)

A smaller priority number has absolute precedence over a larger one.

Selection steps:

1. Scan all processes under their individual locks.
2. Find the smallest priority among all `RUNNABLE` processes.
3. Consider only processes at that best priority.
4. Start the circular search at `scheduler_next[best_priority]`.
5. Select the first runnable process at that priority.
6. Move the cursor to the slot after the selected process.

Simplified pseudocode:

```text
best = 101

for each process:
    with p->lock:
        if p is RUNNABLE and p->priority < best:
            best = p->priority

scan proc[] circularly from scheduler_next[best]
choose the first RUNNABLE process with priority == best
scheduler_next[best] = (chosen_index + 1) % NPROC
```

There is one round-robin cursor for each of the 101 priority levels. A single global cursor produced bias when CPUs switched between priority levels. Independent cursors preserve the last position separately for every priority and prevent that cross-level bias.

Round-robin fairness applies only among processes at the current best priority. Strict priority can still starve lower-priority processes if a higher-priority process remains continuously runnable. Aging is not implemented.

Timer interrupts still preempt the running process and call `yield()`, so this scheduler remains preemptive.

### Lottery Scheduler (`LOTTERY`)

Let `T` be the sum of all tickets held by runnable processes:

```text
T = sum(tickets[i]) for every RUNNABLE process
winning_ticket = random64 % T + 1
```

Selection steps:

1. Read every runnable process's ticket count under its `p->lock`.
2. Store those values in `ticket_snapshot[NPROC]`.
3. Accumulate the total in a 64-bit `total_tickets` value.
4. Combine two `PRNG()` outputs into one 64-bit random number.
5. Select a ticket in the closed range `1..total_tickets`.
6. Walk the cumulative ticket ranges to find the owner of the winning ticket.
7. Reacquire the winner's lock and verify that it is still `RUNNABLE`.
8. Change it to `RUNNING` and perform the context switch.

For process `i`, the theoretical probability of winning one draw is approximately:

```text
P(i) = tickets[i] / sum(tickets of all RUNNABLE processes)
```

More tickets improve long-run CPU share but do not guarantee the next selection. Short observations can vary substantially, so scheduler tests compare aggregate runtime over many timer periods.

## Locking and Multicore Behavior

This version of xv6 does not have one global `ptable.lock`. The process table is an array of independently locked `struct proc` values.

| Lock | Protected state or operation |
|---|---|
| `p->lock` | State and scheduling fields of one process |
| `scheduler_lock` | Selection pass for `PRIORITY` and `LOTTERY` across CPUs |
| `rand_lock` | LCG state and initialization |
| `tickslock` | Global `ticks` counter |
| `pid_lock` | PID allocation |
| `wait_lock` | Parent-child relationships and wait/wakeup correctness |

The custom scheduler lock is acquired before examining candidates and released before `swtch()`. It serializes the multi-step selection decision without remaining locked for the entire process time slice.

The primary scheduler lock order is:

```text
scheduler_lock -> p->lock
```

`getpinfo()`, `setpriority()`, and `settickets()` acquire only one `p->lock` at a time and never acquire `scheduler_lock`, avoiding a reverse lock-order cycle.

With the default `CPUS=3`, up to three processes can be shown as `run` in one `ps` snapshot. A process shown as `runble` may still have run briefly between two snapshots. Process state is instantaneous; runtime deltas are a better fairness measurement.

## Runtime Accounting (`RTIME`)

`clockintr()` checks the process currently assigned to the local CPU. If that process is `RUNNING`, its `runtime` field is incremented under `p->lock`.

```c
struct proc *p = myproc();

if (p) {
  acquire(&p->lock);
  if (p->state == RUNNING)
    p->runtime++;
  release(&p->lock);
}
```

The current timer is scheduled with `r_time() + 1000000`, which is approximately one interrupt every 0.1 seconds in this xv6/QEMU setup. A rough conversion is:

```text
CPU time in seconds ~= RTIME / 10
```

`RTIME` is not exact wall-clock time. It is a count of timer periods during which a process was running on a CPU. On a multicore system, several processes can each gain one runtime tick during approximately the same wall-clock interval.

The global xv6 `ticks` count is incremented only by CPU 0, while per-process runtime can be incremented on every CPU. The sum of all process runtimes can therefore grow faster than `uptime()`.

## Process States

| Kernel state | `ps` text | Meaning |
|---|---|---|
| `UNUSED` | not shown | The process-table slot is free. |
| `USED` | `used` | The slot is allocated but not yet runnable. |
| `SLEEPING` | `sleep` | The process is waiting for an event, child, input, lock, or timer. |
| `RUNNABLE` | `runble` | The process is ready and waiting for a CPU. |
| `RUNNING` | `run` | The process is currently executing on one CPU. |
| `ZOMBIE` | `zombie` | The process exited, but its parent has not called `wait()` yet. |

An orphan is a live process whose parent exited first. xv6 reparents it to `init`. A zombie is different: it has finished execution and retains only its exit information until its parent reaps it with `wait()`.

## User Commands

### `ps`

```text
$ ps
PID     OWNER   PRI     STAT    TICKETS RTIME   COMMAND
1       0       75      runble  1       0       init
2       0       0       sleep   1       0       sh
3       0       0       run     1       0       ps
```

Columns:

| Column | Meaning |
|---|---|
| `PID` | Process identifier |
| `OWNER` | Owner identifier; currently always 0 |
| `PRI` | Priority in `0..100`; smaller is higher |
| `STAT` | Current process state |
| `TICKETS` | Lottery scheduling weight |
| `RTIME` | Timer periods spent running |
| `COMMAND` | Executable name stored in `proc.name` |

### `chpri`

Syntax:

```text
chpri PID PRIORITY
```

Example:

```text
$ chpri 7 20
```

The PID must be positive and the priority must be in `0..100`. The command exits silently on success and prints an error for invalid input or an unknown PID.

### `chtickets`

Syntax:

```text
chtickets PID NUMBER
```

Example:

```text
$ chtickets 7 50
```

The ticket count must be a positive integer. The user-space parser also rejects text and signed integer overflow.

### `spin`

Start CPU-bound workloads in the background:

```text
$ spin &
$ spin &
$ ps
```

`spin` runs an unlimited loop without sleeping. Find its PID with `ps` and stop it with:

```text
$ kill 7
```

xv6 does not provide Bash-style job control. Keep track of test PIDs and terminate background workloads after each manual experiment.

## Tests

Two dedicated user programs test the new functionality: `pstest` and `pritest`.

### `pstest`

`pstest` verifies the basic process-information path:

1. Forks a child.
2. Keeps the child alive in `pause()`.
3. Calls `getpinfo()` and checks that the child's PID is present.
4. Forks and executes the real `ps` command.
5. Checks the `ps` exit status.
6. Kills and waits for the original child.

Example:

```text
$ pstest
pstest: child pid 4 is present; ps output follows
PID     OWNER   PRI     STAT    TICKETS RTIME   COMMAND
...
pstest: OK
```

### Common `pritest` Coverage

The common test section runs with all three schedulers and verifies:

- A newly allocated process starts with exactly one ticket.
- Setting the parent to 17 tickets is reflected by `getpinfo()`.
- A forked child inherits all 17 parent tickets.
- Changing the child to 29 tickets does not change the parent's 17 tickets.
- Zero tickets, negative tickets, and an unknown PID are rejected.
- Invalid ticket changes preserve the previous valid value.
- The real `chtickets` command accepts 41 and rejects 0, `-1`, and text.
- Priority boundaries 0 and 100 are accepted.
- Priorities `-1`, 101, and unknown PIDs are rejected.
- The real `chpri` command accepts a valid value and rejects invalid input.
- Twelve children receive priorities in `0..100` with variation and a reasonable sample mean near 50.
- Four concurrent workers repeatedly call `settickets`, `setpriority`, and `getpinfo` while six `spin` processes run.
- The lock stress test completes 1,200 protected operations without deadlock.

### `DEFAULT` Scheduler Test

The test starts six real `spin` programs behind a pipe start barrier:

- Three receive priority 0 and 100 tickets.
- Three receive priority 100 and one ticket.
- All six run for 60 timer ticks.
- Every runtime delta must be positive.
- The maximum runtime spread must be at most 15 ticks.

Similar runtimes across deliberately opposite metadata values prove that the original scheduler ignores both priority and tickets.

Representative output:

```text
pritest: default round-robin ignores metadata
pritest: default pid=37 priority=0 tickets=100 runtime=34
pritest: default pid=38 priority=0 tickets=100 runtime=29
pritest: default pid=39 priority=0 tickets=100 runtime=29
pritest: default pid=40 priority=100 tickets=1 runtime=30
pritest: default pid=41 priority=100 tickets=1 runtime=29
pritest: default pid=42 priority=100 tickets=1 runtime=29
pritest: OK
```

### `PRIORITY` Scheduler Tests

High-priority preference test:

- Runs five rounds.
- Each round creates 16 reporters at priority 0 and four at priority 100.
- All children wait behind a pipe barrier.
- The first four completion reports must come from priority-0 children.
- Every child must eventually report and exit.

Same-priority round-robin test:

- Creates four workers at priority 50.
- Collects 96 scheduling samples.
- Every worker must receive at least one sample.
- No worker may receive more than 75 percent of all samples.
- A timeout process kills the workers if scheduler progress stops.

Runtime spread test:

- Starts six real `spin` programs at priority 50.
- Measures `RTIME` deltas for 60 ticks.
- Every process must run.
- The maximum and minimum runtime difference must be at most 15 ticks.

Representative output:

```text
pritest: scheduler high-priority preference
pritest: same-priority round-robin fairness
pritest: fair counts 24 24 24 24
pritest: spin round-robin runtime
pritest: OK
```

### `LOTTERY` Scheduler Test

The lottery test uses eight real `spin` programs and two phases:

Phase 1:

- Four processes receive one ticket each.
- Four processes receive 20 tickets each.
- Runtime deltas are collected for 60 ticks.
- The high-ticket group's total runtime must exceed twice the low-ticket total.

Phase 2:

- The ticket assignments are reversed between the same two PID groups.
- Fresh start and end runtime snapshots are collected.
- The newly high-ticket group must now exceed twice the low-ticket total.

Reversing the ticket assignments demonstrates that the observed result comes from ticket weight rather than PID order or process-table position.

Representative output from one successful run:

```text
pritest: lottery phase=1 low=13 high=167
pritest: lottery phase=2 low=11 high=169
pritest: OK
```

Exact lottery values vary between runs. The test checks the group relationship, not equality with these sample numbers.

## Manual Scheduler Experiments

### Priority Experiment

```text
$ spin &
$ spin &
$ ps
$ chpri PID1 1
$ chpri PID2 50
$ ps
```

Under `PRIORITY`, the process with numeric priority 1 is preferred over priority 50. If several processes share the best priority, their `RTIME` values should remain close over a long observation window.

### Lottery Experiment

```text
$ spin &
$ spin &
$ chtickets PID1 1
$ chtickets PID2 20
$ ps
... wait ...
$ ps
```

The 20-ticket process should accumulate runtime faster over many selections. One short snapshot is not sufficient for a statistical scheduler. Swap the ticket counts and repeat to rule out PID or table-position bias.

### Cleaning Up Workloads

```text
$ kill PID1
$ kill PID2
$ ps
```

`kill()` sets the target's killed flag. The process exits when it next reaches the relevant trap or wakeup path. Its parent must call `wait()` before the final zombie entry is released.

## Troubleshooting

### RISC-V GCC or binutils cannot be found

If the Makefile prints:

```text
Couldn't find a riscv64 version of GCC/binutils
```

Verify that the cross tools are installed and available in `PATH`. If the tools use a non-default prefix, specify it explicitly:

```sh
make qemu TOOLPREFIX=riscv64-unknown-elf-
```

Using the macOS host Clang without a RISC-V cross toolchain produces an error similar to:

```text
clang: error: unsupported argument 'rv64gc' to option '-march='
```

### QEMU cannot be found

```sh
command -v qemu-system-riscv64
```

If this prints nothing, install QEMU or add the Homebrew binary directory to `PATH`.

### A new command reports `exec ... failed`

The program is probably missing from an old `fs.img`. Rebuild the complete file-system image:

```sh
make clean
make qemu SCHEDULER=PRIORITY
```

Also check command spelling. The priority command is `chpri`, not `chrpi`.

### QEMU does not exit

Use `Ctrl-a`, release the keys, and press `x` in the QEMU terminal. If the terminal does not pass the escape sequence, find QEMU from another host terminal:

```sh
ps aux | grep qemu-system-riscv64
kill PID
```

### The shell prompt does not return

Strict priority can starve lower-priority processes when CPU-bound higher-priority workloads remain runnable. The main interactive commands receive priority 0 to preserve system control, but uncontrolled experiments can still make the system difficult to use. Exit QEMU and restart with a clean process table if necessary.

### `RTIME` increases for a process shown as `runble`

`ps` reports the process state at one instant. The process may have run and received a timer interrupt between the previous snapshot and the current one, then returned to `RUNNABLE`. Compare runtime deltas over a longer interval.

### Lottery output changes between runs

Lottery scheduling is probabilistic. Use longer measurement windows and compare aggregate runtime across groups. Do not require one exact ordering or exact sample output.

### `fsblocks` causes an unused-variable build error

Newer compilers can report `fsblocks` as set but unused, and xv6 builds with `-Werror`. The project explicitly evaluates it with:

```c
(void)fsblocks;
```

This preserves the existing test logic while satisfying the compiler.

## Design Limitations

- xv6 has no account or credential model, so `OWNER` is currently always 0.
- There is no permission policy for `setpriority()` or `settickets()`; any process can target an existing PID.
- Strict priority has no aging and can starve lower-priority processes.
- Lottery scheduling gives statistical, not deterministic, proportional share.
- The LCG is intended for educational scheduling, not security.
- `RTIME` counts CPU timer periods, not exact milliseconds, wall time, or separate user/kernel time.
- `getpinfo()` provides a row-consistent snapshot, not one atomic transaction over the complete table.
- Scheduler selection happens at compile time and cannot be changed while xv6 is running.
- This project does not add user-space threads; every `ps` row represents a process.
