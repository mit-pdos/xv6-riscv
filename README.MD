# توسعه مدیریت فرایند و زمان‌بندی در xv6 RISC-V

این مخزن نسخه توسعه‌یافته سیستم‌عامل آموزشی xv6 برای معماری RISC-V است. در این پروژه، ابزار مشاهده فرایندها، سه فراخوان سیستمی جدید، ثبت زمان اجرای فرایند، تغییر اولویت و بلیت از فضای کاربر، و سه روش زمان‌بندی قابل انتخاب پیاده‌سازی شده‌اند.

## نشانی مخزن

- مخزن پروژه: <https://github.com/amirhdeh/xv6-riscv>
- شاخه نهایی: `ps-init`
- مبنای اصلی: <https://github.com/mit-pdos/xv6-riscv>

برای دریافت مستقیم نسخه نهایی:

```sh
git clone --branch ps-init https://github.com/amirhdeh/xv6-riscv.git
cd xv6-riscv
```

## امکانات افزوده‌شده

- ساختار مشترک `pinfo` برای انتقال اطلاعات جدول فرایند از هسته به فضای کاربر
- فراخوان سیستمی `getpinfo(struct pinfo *)`
- فرمان `ps` با ستون‌های PID، مالک، اولویت، وضعیت، تعداد بلیت، زمان اجرا و نام فرمان
- اولویت عددی از ۰ تا ۱۰۰؛ عدد کمتر به معنی اولویت بالاتر است
- تولید اولویت اولیه شبه‌تصادفی در بازه ۰ تا ۱۰۰
- فراخوان سیستمی `setpriority(int pid, int priority)` و فرمان `chpri`
- تعداد بلیت اولیه برابر ۱ و ارث‌بری بلیت هنگام `fork`
- فراخوان سیستمی `settickets(int pid, int number)` و فرمان `chtickets`
- مولد عدد شبه‌تصادفی `PRNG` بر پایه LCG و seed اولیه از `ticks`
- ثبت `RTIME` بر حسب وقفه‌های تایمر سپری‌شده در حالت `RUNNING`
- بار کاری پردازنده‌ای `spin` برای آزمایش زمان‌بندها
- سه زمان‌بند قابل انتخاب در زمان کامپایل: xv6 اصلی، اولویت و لاتاری
- آزمون‌های عملکردی، آماری، هم‌زمانی، عدم بن‌بست و ارث‌بری بلیت

## ساختار اطلاعات فرایند

فیلدهای زیر به `struct proc` در `kernel/proc.h` افزوده شده‌اند:

| فیلد | معنی |
|---|---|
| `owner` | شناسه مالک فرایند؛ در xv6 فعلی همه فرایندها مالک ۰ دارند |
| `priority` | اولویت در بازه ۰ تا ۱۰۰؛ ۰ بالاترین اولویت است |
| `tickets` | وزن فرایند در زمان‌بند لاتاری؛ همیشه حداقل ۱ است |
| `runtime` | تعداد وقفه‌های تایمری که فرایند در زمان آن‌ها `RUNNING` بوده است |

ساختار `kernel/pinfo.h` در هسته و برنامه‌های فضای کاربر قابل استفاده است. این ساختار برای هر خانه جدول فرایند، فیلدهای `inuse`، `pid`، `owner`، `priority`، `status`، `tickets`، `runtime` و `name` را نگه می‌دارد.

## فراخوان‌های سیستمی

سه شماره جدید در `kernel/syscall.h` تعریف شده است:

| شماره | رابط فضای کاربر | وظیفه |
|---:|---|---|
| ۲۳ | `getpinfo(struct pinfo *info)` | دریافت تصویر اطلاعات فرایندها |
| ۲۴ | `setpriority(int pid, int priority)` | تغییر اولویت یک PID معتبر |
| ۲۵ | `settickets(int pid, int number)` | تغییر تعداد بلیت یک PID معتبر |

مسیر هر فراخوان به صورت زیر است:

```text
برنامه کاربر -> user/usys.pl -> kernel/syscall.c -> kernel/sysproc.c -> kernel/proc.c
```

در `getpinfo` هر خانه جدول فرایند با `p->lock` خوانده می‌شود. بنابراین فیلدهای هر فرایند هنگام کپی سازگار هستند. بعد از تکمیل ساختار محلی هسته، کل ساختار با `copyout` به فضای آدرس فرایند فراخواننده منتقل می‌شود.

در نسخه جدید xv6 قفل سراسری با نام `ptable.lock` وجود ندارد. جدول فرایند از آرایه `proc[NPROC]` و قفل مستقل هر عضو ساخته شده است. توابع `getpinfo`، `ksetpriority` و `ksettickets` هنگام دسترسی به هر عضو، همان `p->lock` را می‌گیرند.

## مقداردهی و ارث‌بری

در `allocproc` مقادیر اولیه زیر تنظیم می‌شوند:

```text
owner    = 0
priority = PRNG() % 101
tickets  = 1
runtime  = 0
```

در `fork`، فرزند `owner` و `tickets` والد را به ارث می‌برد. اولویت فرزند به طور عادی از مقدار شبه‌تصادفی تولیدشده در `allocproc` می‌آید. برای جلوگیری از گرسنگی پوسته هنگام اجرای فرمان‌ها، فرزند مستقیم `sh` ابتدا اولویت ۰ می‌گیرد؛ سپس `exec` برای فرمان‌های عادی پوسته یک اولویت تازه در بازه ۰ تا ۱۰۰ تولید می‌کند. فرمان‌های تعاملی `sh`، `ps`، `kill`، `chpri` و `chtickets` در اولویت ۰ نگه داشته می‌شوند تا حتی زیر بار شدید قابل اجرا باشند. `spin` جزو این فهرست نیست.

## مولد عدد شبه‌تصادفی

تابع `PRNG` در `kernel/proc.c` یک Linear Congruential Generator است:

```text
state(n+1) = (1103515245 * state(n) + 12345) mod 2^32
```

در نخستین فراخوان، مقدار `ticks` تحت حفاظت `tickslock` به عنوان seed خوانده می‌شود. وضعیت داخلی مولد با `rand_lock` محافظت می‌شود تا فراخوان‌های هم‌زمان چند هسته باعث race نشوند. سرریز نوع بدون علامت `uint` همان پیمانه `2^32` را ایجاد می‌کند.

## انتخاب زمان‌بند

انتخاب زمان‌بند در زمان کامپایل و با متغیر `SCHEDULER` انجام می‌شود. اگر این متغیر داده نشود، زمان‌بند اصلی xv6 فعال است.

```sh
# زمان‌بند اصلی xv6، حالت پیش‌فرض
make qemu

# زمان‌بند اولویت
make qemu SCHEDULER=PRIORITY

# زمان‌بند لاتاری
make qemu SCHEDULER=LOTTERY
```

مقدار صریح `SCHEDULER=DEFAULT` نیز پذیرفته می‌شود. هر مقدار دیگری در Makefile خطا می‌دهد. فایل‌های `kernel/proc.o` و `user/pritest.o` هنگام تغییر حالت دوباره ساخته می‌شوند؛ بنابراین برای جابه‌جایی میان زمان‌بندها معمولاً نیازی به `make clean` نیست.

### زمان‌بند اصلی xv6 (`DEFAULT`)

این شاخه همان حلقه اصلی xv6 را بدون اعمال اولویت یا بلیت اجرا می‌کند. هر CPU آرایه `proc` را پیمایش می‌کند، قفل هر عضو را می‌گیرد و هر فرایند `RUNNABLE` را اجرا می‌کند. اگر فرایند قابل اجرایی وجود نداشته باشد، دستور `wfi` تا وقفه بعدی CPU را متوقف می‌کند.

در این حالت مقادیر `priority` و `tickets` همچنان قابل مشاهده و تغییر هستند، ولی در انتخاب فرایند دخالت ندارند.

### زمان‌بند اولویت (`PRIORITY`)

الگوریتم انتخاب در هر دور:

1. تمام فرایندها با قفل مستقلشان بررسی می‌شوند.
2. کوچک‌ترین عدد اولویت بین فرایندهای `RUNNABLE` پیدا می‌شود.
3. فقط فرایندهای همان سطح اولویت نامزد اجرا هستند.
4. آرایه `scheduler_next[101]` برای هر سطح اولویت یک مکان‌نمای مستقل نگه می‌دارد.
5. جست‌وجو از مکان‌نمای آن سطح آغاز می‌شود و اولین نامزد اجرا می‌شود.
6. مکان‌نما به خانه بعد از فرایند انتخاب‌شده منتقل می‌شود.

بنابراین اولویت بالاتر به صورت سخت‌گیرانه مقدم است و فرایندهای هم‌اولویت به روش round-robin نوبت می‌گیرند. وجود مکان‌نمای جداگانه برای هر اولویت از سوگیری ناشی از یک مکان‌نمای سراسری جلوگیری می‌کند.

این روش ممکن است فرایندهای با اولویت پایین را گرسنه کند؛ اگر همیشه فرایندی با عدد اولویت کمتر آماده باشد، فرایند پایین‌تر انتخاب نمی‌شود. اولویت صفر فرمان‌های تعاملی برای حفظ امکان کنترل سیستم در بارهای آزمایشی است.

### زمان‌بند لاتاری (`LOTTERY`)

الگوریتم انتخاب در هر دور:

1. از تعداد بلیت تمام فرایندهای `RUNNABLE` یک snapshot گرفته می‌شود.
2. مجموع بلیت‌ها در متغیر ۶۴ بیتی `total_tickets` محاسبه می‌شود.
3. دو خروجی ۳۲ بیتی `PRNG` به یک مقدار ۶۴ بیتی تبدیل می‌شوند.
4. بلیت برنده در بازه بسته `1..total_tickets` انتخاب می‌شود.
5. با کم‌کردن بازه بلیت هر فرایند، صاحب بلیت برنده مشخص می‌شود.
6. وضعیت برنده دوباره زیر `p->lock` بررسی می‌شود و در صورت `RUNNABLE` بودن اجرا می‌شود.

برای فرایند `i` با `tickets[i]` بلیت، احتمال نظری انتخاب در یک قرعه برابر است با:

```text
P(i) = tickets[i] / sum(tickets of RUNNABLE processes)
```

فراخوان `settickets` مقدار صفر و منفی را رد می‌کند؛ در نتیجه فرایند قابل اجرا هیچ‌گاه عمداً از قرعه حذف نمی‌شود. تغییر بلیت بلافاصله در دور بعدی زمان‌بندی دیده می‌شود.

## قفل‌گذاری و هم‌زمانی چند هسته‌ای

- `p->lock`: محافظ وضعیت و اطلاعات زمان‌بندی هر فرایند
- `scheduler_lock`: فقط در حالت‌های `PRIORITY` و `LOTTERY`، برای سری‌سازی مرحله انتخاب میان CPUها
- `rand_lock`: محافظ state مولد LCG
- `tickslock`: محافظ شمارنده سراسری `ticks`
- `pid_lock`: محافظ تخصیص PID
- `wait_lock`: محافظ رابطه والد و فرزند و جلوگیری از wakeup ازدست‌رفته

`scheduler_lock` پیش از بررسی نامزدها گرفته می‌شود، اما پیش از `swtch` آزاد می‌شود؛ بنابراین قفل سراسری انتخاب در تمام مدت اجرای فرایند نگه داشته نمی‌شود. ترتیب اصلی در مسیر زمان‌بند `scheduler_lock` سپس `p->lock` است. مسیرهای تغییر اولویت، بلیت و دریافت اطلاعات فقط `p->lock` را می‌گیرند.

با مقدار پیش‌فرض `CPUS=3` ممکن است در خروجی `ps` هم‌زمان تا سه فرایند در حالت `run` دیده شوند. snapshot کل جدول اتمیک نیست، چون هر سطر جداگانه قفل می‌شود؛ با این حال هر سطر به تنهایی سازگار است.

## زمان اجرای فرایند (`RTIME`)

در `clockintr`، اگر روی CPU جاری فرایندی در حالت `RUNNING` باشد، `runtime` آن فرایند زیر `p->lock` یک واحد افزایش می‌یابد. در تنظیم فعلی QEMU فاصله تایمر تقریباً ۱۰۰ میلی‌ثانیه است؛ بنابراین مقدار تقریبی زمان CPU برابر است با:

```text
CPU time in seconds ~= RTIME / 10
```

`RTIME` زمان دیواری نیست و فقط وقفه‌هایی را می‌شمارد که فرایند واقعاً روی یک CPU اجرا شده است. در سیستم چند هسته‌ای مجموع افزایش `RTIME` همه فرایندها می‌تواند در یک بازه دیواری از افزایش `uptime` بیشتر باشد.

## وضعیت‌های فرایند

| وضعیت هسته | متن در `ps` | توضیح |
|---|---|---|
| `USED` | `used` | ساختار رزرو شده ولی هنوز آماده اجرا نیست |
| `SLEEPING` | `sleep` | منتظر رویداد، ورودی، child یا تایمر است |
| `RUNNABLE` | `runble` | آماده اجرا و منتظر CPU است |
| `RUNNING` | `run` | در لحظه snapshot روی یک CPU اجرا می‌شود |
| `ZOMBIE` | `zombie` | خاتمه یافته ولی والد هنوز `wait` نکرده است |

فرایند orphan فرایندی است که والدش پیش از آن خاتمه یافته؛ xv6 آن را به `init` می‌سپارد. zombie با orphan یکسان نیست: zombie دیگر اجرا نمی‌شود و فقط نتیجه خروجش تا زمان `wait` نگهداری می‌شود.

## پیش‌نیازها

پروژه به ابزار GNU Make، کامپایلر و binutils برای RISC-V و QEMU با پشتیبانی `riscv64` نیاز دارد.

### macOS با Homebrew

```sh
xcode-select --install
brew install qemu riscv-tools
```

بررسی نصب:

```sh
qemu-system-riscv64 --version
riscv64-unknown-elf-gcc --version
riscv64-unknown-elf-objdump --version
```

اگر دانلود Homebrew پشت V2Ray انجام می‌شود و پورت ۱۰۸۰۸ یک SOCKS5 proxy است:

```sh
export ALL_PROXY=socks5h://127.0.0.1:10808
brew update
```

نوع proxy باید با تنظیم واقعی V2Ray یکسان باشد؛ برای درگاه HTTP از `HTTP_PROXY` و `HTTPS_PROXY` استفاده کنید.

### Ubuntu/Debian

```sh
sudo apt update
sudo apt install git build-essential gdb-multiarch qemu-system-misc \
  gcc-riscv64-linux-gnu binutils-riscv64-linux-gnu
```

Makefile پیشوند ابزار را از بین گزینه‌هایی مانند `riscv64-unknown-elf-` و `riscv64-linux-gnu-` به طور خودکار تشخیص می‌دهد.

## اجرای پروژه

از ریشه مخزن یکی از حالت‌های زمان‌بند را بسازید:

```sh
make clean
make qemu
```

پس از مشاهده پیام زیر، پوسته آماده است:

```text
init: starting sh
$
```

برای اجرای تک‌هسته‌ای یا تغییر تعداد CPUها:

```sh
make qemu CPUS=1
make qemu SCHEDULER=PRIORITY CPUS=3
```

برای خروج از QEMU در حالت `-nographic`، `Ctrl-a` را فشار دهید، کلیدها را رها کنید و سپس `x` را بزنید. نوشتن `quit` داخل پوسته xv6 درست نیست، چون xv6 آن را نام یک برنامه فرض می‌کند.

## فرمان‌های جدید

### نمایش فرایندها

```sh
$ ps
PID     OWNER   PRI     STAT    TICKETS RTIME   COMMAND
1       0       75      runble  1       0       init
2       0       0       sleep   1       0       sh
3       0       0       run     1       0       ps
```

### تغییر اولویت

```sh
$ chpri 7 20
```

قالب فرمان `chpri PID PRIORITY` است. PID باید مثبت و اولویت باید بین ۰ و ۱۰۰ باشد.

### تغییر بلیت

```sh
$ chtickets 7 50
```

قالب فرمان `chtickets PID NUMBER` است. تعداد بلیت باید عدد صحیح مثبت باشد.

### ایجاد بار CPU

```sh
$ spin &
$ spin &
$ ps
```

`spin` یک حلقه نامحدود بدون sleep است. برای خاتمه هر نمونه PID آن را از `ps` پیدا کنید:

```sh
$ kill 7
```

xv6 مدیریت job مانند Bash ندارد؛ بنابراین PIDها را یادداشت کنید و فرایندهای آزمایشی را پس از آزمون خاتمه دهید.

## آزمون‌ها

### آزمون `pstest`

این آزمون یک فرزند ایجاد می‌کند، آن را برای مدتی در حالت sleep نگه می‌دارد، با `getpinfo` وجود PID را کنترل می‌کند، خروجی واقعی `ps` را اجرا می‌کند و در پایان child را kill و reap می‌کند.

```sh
$ pstest
pstest: child pid 4 is present; ps output follows
...
pstest: OK
```

### آزمون جامع `pritest`

بخش مشترک این آزمون در هر سه زمان‌بند موارد زیر را بررسی می‌کند:

- مقدار اولیه یک بلیت برای فرایند تازه
- تنظیم بلیت والد روی ۱۷، اجرای `fork` و برابری بلیت فرزند با والد
- رد بلیت صفر، منفی و PID ناموجود بدون تغییر مقدار قبلی
- تغییر بلیت child مستقل از والد
- ورودی معتبر و نامعتبر فرمان `chtickets`
- مرزهای اولویت ۰ و ۱۰۰ و رد مقادیر خارج بازه
- ورودی معتبر و نامعتبر فرمان `chpri`
- قرارداشتن اولویت‌های تصادفی در بازه، تنوع نمونه‌ها و میانگین معقول نزدیک ۵۰
- اجرای هم‌زمان چهار worker روی شش `spin` و انجام ۱۲۰۰ عملیات قفل‌شده

در حالت `DEFAULT`، شش `spin` ساخته می‌شوند؛ نیمی اولویت ۰ و ۱۰۰ بلیت و نیمی اولویت ۱۰۰ و یک بلیت می‌گیرند. نزدیک‌بودن `RTIME` آن‌ها نشان می‌دهد زمان‌بند اصلی metadata جدید را نادیده می‌گیرد.

در حالت `PRIORITY`، آزمون پنج دور رقابت بین ۱۶ فرایند اولویت ۰ و چهار فرایند اولویت ۱۰۰ اجرا می‌کند و تقدم گروه اول را می‌سنجد. سپس چهار worker هم‌اولویت ۹۶ نمونه تولید می‌کنند تا عدم گرسنگی و round-robin بررسی شود. آزمون شش `spin` نیز پخش نزدیک زمان CPU را با اختلاف حداکثر ۱۵ tick کنترل می‌کند.

در حالت `LOTTERY`، هشت `spin` در دو گروه قرار می‌گیرند. گروه اول یک بلیت و گروه دوم ۲۰ بلیت دارد. بعد از ۶۰ tick، بلیت دو گروه جابه‌جا می‌شود و آزمون دوباره اجرا می‌شود. در هر دو فاز مجموع `RTIME` گروه پربلیت باید بیش از دو برابر گروه کم‌بلیت باشد.

اجرای آزمون‌ها:

```sh
# حالت اصلی xv6
make qemu
$ pstest

```

## عیب‌یابی

### ابزار RISC-V پیدا نمی‌شود

اگر Makefile پیام `Couldn't find a riscv64 version of GCC/binutils` داد، وجود `riscv64-unknown-elf-objdump` یا `riscv64-linux-gnu-objdump` را در `PATH` بررسی کنید. در صورت نصب پیشوند متفاوت، آن را صریح بدهید:

```sh
make qemu TOOLPREFIX=riscv64-unknown-elf-
```

استفاده از Clang میزبان macOS بدون cross-toolchain مناسب باعث خطای `unsupported argument 'rv64gc'` می‌شود.

### QEMU پیدا نمی‌شود

```sh
command -v qemu-system-riscv64
```

در macOS مسیر Homebrew روی Apple Silicon معمولاً `/opt/homebrew/bin` است. این مسیر باید در `PATH` باشد.

### فرمان جدید با `exec ... failed` اجرا نمی‌شود

این خطا معمولاً یعنی `fs.img` پیش از اضافه‌شدن برنامه ساخته شده است. تصویر فایل‌سیستم را بازسازی کنید:

```sh
make clean
make qemu SCHEDULER=PRIORITY
```

### خروج از QEMU کار نمی‌کند

در همان ترمینالی که QEMU اجرا شده، توالی `Ctrl-a` سپس `x` را وارد کنید. اگر ترمینال توالی را دریافت نکرد، از ترمینال دیگری PID را پیدا و خاتمه دهید:

```sh
ps aux | grep qemu-system-riscv64
kill PID
```

### تفسیر خروجی چند هسته‌ای

در `CPUS=3` مشاهده چند `run` طبیعی است. همچنین snapshotهای متوالی ممکن است یک فرایند را بیشتر در حالت `run` نشان دهند؛ `ps` فقط یک لحظه را ثبت می‌کند. برای مقایسه منصفانه زمان CPU از اختلاف `RTIME` در یک بازه استفاده کنید، نه تعداد دفعات مشاهده ستون `STAT`.

## فایل‌های اصلی پروژه

| فایل | مسئولیت |
|---|---|
| `kernel/proc.h` | فیلدهای فرایند و وضعیت‌ها |
| `kernel/pinfo.h` | قرارداد مشترک اطلاعات فرایند |
| `kernel/proc.c` | PRNG، مقداردهی، fork، تغییر فیلدها و سه زمان‌بند |
| `kernel/sysproc.c` | بدنه فراخوان‌های سیستمی جدید |
| `kernel/syscall.h` و `kernel/syscall.c` | شماره‌گذاری و dispatch فراخوان‌ها |
| `kernel/trap.c` | افزایش `runtime` در وقفه تایمر |
| `kernel/exec.c` | نام فرمان و اولویت فرمان‌های تعاملی |
| `user/ps.c` | نمایش جدول فرایند |
| `user/chpri.c` | رابط پوسته برای تغییر اولویت |
| `user/chtickets.c` | رابط پوسته برای تغییر بلیت |
| `user/spin.c` | بار CPU نامحدود |
| `user/pstest.c` | آزمون پایه `getpinfo` و `ps` |
| `user/pritest.c` | مجموعه آزمون جامع سه زمان‌بند و هم‌زمانی |
| `Makefile` | انتخاب زمان‌بند و افزودن برنامه‌ها به `fs.img` |

## محدودیت‌های آگاهانه

- مدل کاربر و مجوز در xv6 پیاده‌سازی نشده است؛ بنابراین `OWNER` در حال حاضر ۰ است.
- زمان‌بند اولویت aging ندارد و گرسنگی اولویت‌های پایین ممکن است.
- لاتاری تضمین قطعی برای هر انتخاب منفرد ندارد؛ انصاف آن آماری و بلندمدت است.
- `RTIME` دقتی برابر دوره وقفه تایمر دارد و زمان دقیق نانوثانیه‌ای نیست.
- `getpinfo` یک snapshot سطر‌به‌سطر است، نه تراکنش اتمیک کل جدول.
- انتخاب زمان‌بند compile-time است و در زمان اجرای هسته قابل تعویض نیست.

## پاک‌سازی خروجی ساخت

```sh
make clean
```

این فرمان kernel، برنامه‌های کاربر، فایل‌های object و `fs.img` تولیدشده را حذف می‌کند.
